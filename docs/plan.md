# 路线图

主安装流程现已改为单 JAR drop-in：检查与预下载在运行中进行，helper 等整个 JVM 退出后安装。以下区分实现目标、既有证据与待验证事项，不保证首次扫描前最新。

## 1. 单 JAR 安装与生命周期

**本次目标：** companion 内嵌独立 helper；用户只需将一个 JAR 放进 mods。新配置默认本地开发关闭，已有值保留；仅显式本地开发开关暂停 Folkways/依赖，自身更新独立。

**验收：** 无外部文件手动配置的真实首装；官方两版本退出后升级；归属与高水位保留；无残留活 helper；Folkways 开关与自身更新开关分别贯穿子进程。结果见 [验证说明](verification.md)。

## 2. 重开竞态与恢复

**本次目标：** ctor 提前登记 lease，持锁检查 journal/安装标记；helper 每次修改重查 lease 与保护，冲突时拒绝混代加载。

**验收：** helper 各替换阶段与新 JVM 的可重复重叠测试，包括 helper 已退出、Mod ctor 才晚到的情况；中断时保留可恢复证据。不要将逐文件 rename 宣称为多文件原子事务。

## 3. 运行时与命令

**已有：** 游戏内轮询、提示和预下载；OP 4 正常停止与取消倒计时。

**已本地验收：** 只安装 updater 的真实 NeoForge 专服中，helper 重启授权、正常存档、整 JVM 重启、原世界重开、限额拒绝保活与正常关闭。使用测试构建，未测试完整 Folkways 包或真实玩家。

**后续：** 完整客户端重启需启动器账号/会话接入；当前不能重启集成服务器来冒充客户端更新。

## 4. 公开发行与自身更新

**已有：** Windows/Linux CI、可信主分支与版本 tag 发布、官方 API 摘要和成功 CI 身份；公开单 JAR 14.1→14.2 在 Windows 的退出后自身更新验证，以及外部 seed 的 6.1→7.1 历史验证。

**后续验收：** Minecraft 客户端内的实际网络升级与更多启动器流程；不把 Java 进程网络实验或旧 seed 结果当作客户端证明。首次手动安装仍是信任步骤。

**本次开关契约验收：** local=true 仍可自身检查、预下载、退出后安装和恢复；same-hash 改名重绑定，官方手动升级验证后恢复托管；未知本地身份不自动打开本地开发，也不顺带停用 Folkways。过去旧 policy 的结果不替代这些新场景。

## 5. Folkways 官方首装与签名镜像

**本次目标：** 默认从所选仓库的官方 GitHub 发行首装/更新，空实例准备 Core、Vanilla 与缺失的 LDLib2；客户端提供可用的配置入口。显式本地开发开关保护 Folkways/依赖，不静默接管已有本地包。

**验收：** 使用当前官方资产和真实依赖加载隔离客户端，检查零安装归属、坏摘要、缺库/旧库、无发行渠道、切源、逐文件中断恢复及开发保护。用户正在运行的实例不作为自动部署目标。

**已有：** 两源五渠道、五组件/按需下载、只读 fetch、离线签名、本地发布、不可变正式归档和 latest 指针；公开外链路径有实际验证。

**延期：** 公共自动签名、受限生产写入适配器和持久二进制归档。默认官方 GitHub 来源和 updater 自身更新不依赖这些服务；显式签名来源仍必须有可信清单与公钥。

## 6. 长期可靠性

完整模组包/目标存档、Linux/Windows 真实安装故障矩阵、客户端启动器体验与断电耐久性逐步验收。当前外链归档不能保证上游删除后仍能获取二进制。
